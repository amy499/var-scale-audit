**VAR cfg schedule.** Upstream `VAR.autoregressive_infer_cfg` (`third_party/VAR/models/var.py`) uses
`t = cfg * si / (num_scales - 1)` at scale `si`, so the guidance ramps linearly from 0 at the first
scale (1x1) to 1.5 at the last (16x16). We use it unchanged. This closes the v1.0 open item
"constant or scheduled".

### ⚠ Verify the index mapping before the first real sweep

Several ImageNet label lists in circulation are wrong for our purposes: some are
1-indexed (MATLAB-style), and some use a completely different class ordering. The
indices above are the standard 0-indexed ILSVRC-2012 ordering, which is what both
VAR and DiT ImageNet checkpoints are trained against.

**Required check (P3, before Gate A):** look at images from every class and confirm each
one is the right breed. A silent off-by-one here would poison every result in the project.
`jobs/baseline.pbs` writes one contact sheet per model (`contact_var_d20.png`, `contact_dit.png`:
one row per class, its first 8 images) for this check. The WNIDs above are the ground truth;
cross-check them against the label file shipped with each checkpoint rather than trusting any
list found online, including this one.

## 3. Seeds (frozen)

Master seed: **`61320017`**

**One seed per image.** The runner gives every manifest row its own generator, seeded from that
row's seed (`runner/generate.py`), so an image does not depend on the batch size or on the other
rows. v1.1 therefore derives one seed per image (224 in total) rather than one per batch.

The seeds are `numpy.random.SeedSequence` output, which is stable across numpy versions and
platforms. They are taken in order: class 151 gets seeds 0–31, class 153 gets 32–63, and so on,
up to class 258 with 192–223.

```python
import numpy as np
seeds = np.random.SeedSequence(61320017).generate_state(224, dtype=np.uint32) % (2**31 - 1)
classes = [151, 153, 162, 207, 235, 254, 258]
rows = [(c, int(seeds[k * 32 + i])) for k, c in enumerate(classes) for i in range(32)]
```

`scripts/manifest/make_manifest_v1_1.py` writes these rows to `manifest/frozen_v1_1.csv`
(header `class_id,seed`, LF line endings, 224 rows). It checks that all 224 seeds are unique,
that the file loads with `runner.manifest.load_manifest`, and that the row count is a multiple of 16.

**Relation to v1.0.** `SeedSequence.generate_state` is prefix-consistent: asking for 224 values
returns v1.0's 14 values, followed by 210 more. So the first 14 per-image seeds (rows 1–14, all class
151, seeds 0–13) equal v1.0's 14 batch seeds, `500681170` … `1465473736`, in order. They are now
used as image seeds, all for class 151, so no v1.0 image is reproduced by v1.1.

### How to generate

```bash
python -m runner.generate --config configs/var_d20.yaml    --manifest manifest/frozen_v1_1.csv --batch-size 16 --out-dir <dir>
python -m runner.generate --config configs/dit_xl2_256.yaml --manifest manifest/frozen_v1_1.csv --batch-size 16 --out-dir <dir>
```

Use the runner rather than calling `torch.manual_seed` and the model yourself. The runner sets the
precision, the attention kernel and the per-row generators from the config, and records them all.
The clean baseline is `jobs/baseline.pbs`.

### ⚠ Two things that will silently break reproducibility

1. **Changing the config, the manifest or the runner changes the images.** With per-image seeds,
   the batch size does not change the images in principle (the runner's design; measured for VAR
   fp32 in `jobs/phase3_check.pbs`, step "batch"). Batch 16 is still the team setting, so runs stay
   comparable in time and memory. If your GPU cannot fit batch 16, raise it with the team rather
   than quietly halving it.
2. **Seeds do not match images across VAR and DiT.** The two models consume randomness
   completely differently. Seed 12345 on VAR and seed 12345 on DiT give two unrelated
   images, not a matched pair. Seeds guarantee reproducibility *within* one model +
   settings combination, nothing more. Do not write 'matched samples' in the report.

## 4. Output convention

The layout is whatever `runner.generate` writes; there is no folder per image. For a
`--manifest` run into `--out-dir <dir>`:

```
<dir>/
    class<cccc>_seed<s>.png   # the finished image, e.g. class0151_seed500681170.png
    class<cccc>_seed<s>.pt    # the raw output tensor
    run.json                  # settings, environment, stage table, and per row: class_id, seed,
                              # file stem, tensor sha256, generator state sha256
```

Clean baselines are generated and saved **before** any intervention runs, per the
project plan. P2 owns the final logging/result schema; this is the naming layer only.
